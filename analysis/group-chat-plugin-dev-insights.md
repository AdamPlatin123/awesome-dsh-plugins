## 2. 对插件开发者的关键启示（7 条）

1. **内测期 = 接口决策窗口，过期不候**。官方明示"现在提的 issue 还有被纳入版本修改的可能性，开源后上万 issue 只能忽视"（[信号 #0]），且官方在群里反复引导"任何 bug 和建议记录到 dsh2026/issues，我们保证能看到"（[信号 #93]、[信号 #91]）。插件作者应在窗口期内把协议/格式/生命周期类诉求以 issue 形式钉死。

2. **插件系统是架构内核但尚未完工，接口漂移是常态**。Cordis 底座"一切皆插件（包括 agent-loop）"（[Issue #171]），但官方自己承认"插件机制还没有做好"（[信号 #84]），hooks 桥事件面有限、安全类插件无从挂载（[Issue #189]），动态装卸资源清理有 bug（[Issue #106]）。插件作者要把"接口变更预期"写进维护策略，而非假设 API 稳定。

3. **格式/协议正在两代并存与对齐中**：静态 `.dsh-plugin/package.json`（skills + MCP 子进程）与动态 `dsh.plugin.json`（同进程 import + Cordis 生命周期）能力面不重叠（详见 `plugin-formats.md`）；同时群聊信号显示 ContentBlock 在 harness/MCP/ACP 三协议"同名不同物"（[Issue #47]），且有人建议直接向 MCP 规范对齐（[信号 #64]）。**结论：能力交付走静态格式（子进程隔离、稳），需要同进程行为（工具/hooks/命令）才走动态格式，且语义对齐 MCP 是安全选择。**

4. **skills 是当前最高频、也最痛的插件形态**：目录规范未定（`.claude/skills` 不扫描，迁移静默失效 [Issue #67]）、无生效可见性（CLI/TUI 均无 skills 列表 [Issue #68/#69]）、Web 端 `/skill:` 与 `disable-model-invocation` 失效（[Issue #62]）、目录变更缓存不失效（[Issue #208]）。开发者交付 skill 时应提供自检脚本并明确声明支持的目录与入口。

5. **构建链与依赖锁是最大入场门槛**：pnpm 版本不校验导致锁文件漂移（[信号 #108]）、`@cordisjs/plugin-loader` 为 rc 版本需显式声明（[信号 #111]）、Web 构建未纳入安装脚本（[信号 #118]）、Windows 无安装脚本（[信号 #116]）。插件必须自带可复现构建（锁 pnpm/node，社区共识 nvm node 24，[信号 #80]），不能假设宿主环境。

6. **贡献与分发机制已有人情化约定，但无系统化通道**：官方"暂时没有机制共享给群友"，贡献路径是"在自己 repo 提 PR + 群内先确认避免撞车"（[信号 #88]）；群友在提议官方开插件私有仓库（[信号 #9]），官方侧已有 `@deepseek-ai/dsh-advisor` 这类插件化贡献被接收（[Issue #30]）。**先沟通、后 PR，是当前唯一防撞车手段。**

7. **多模型集成与"自我进化"是插件生态的两大价值高地**：subagent 指定模型被反复提出（[信号 #95]、issues 汇总组"模型、多模态与协议"：subagent 无法指定模型）、用 skill 补其他模型多模态（[信号 #1]）、codex/claude code 作 subagent（[信号 #85/#96]）；同时"agent 自己安装删除插件"（[信号 #100]）与 dsh-self-iteration skill（[Issue #163]）已在路上。这两块正是插件开发者可以领先官方半步的方向。

## 3. 与我们的 mainline-compat 引擎的呼应

群聊证据直接佐证"插件与 mainline 兼容性监控"的价值，具体有四类支撑：

1. **版本漂移真实且高频**：4 天 4 个快照版本（纪事 07-31 ~ 08-03），每用户独立 repo 且被官方反复推送覆盖（[信号 #99]），"目前暂时没有机制共享给群友"（[信号 #88]）——插件在 mainline 上失效是必然事件，不是假设。这正是 mainline-compat 引擎要监控的第一类对象：官方快照 ref 变化与包版本变化。

2. **补丁失效已有实锤**：ReachStar 发现 trajectory 里有 skill tool 但调用失败（[信号 #50]）——接口行为漂移导致"插件存在但失效"；AUTUMN（[信号 #86]）、夏目贵志（[信号 #101]）的修复必须通过 PR 合回 mainline 才不丢——社区补丁追主线是全职工作，引擎应监控"官方是否已合入等价修复"。

3. **接口变化通知是明确需求**：群友要求"崔佬在正在解决的 issue 下回应，这样就不怕改重了"（[信号 #83]）、"总仓让大家提 issue 标明复现流程和官方正在做的进度"（[信号 #103]）、"issue 仓库加点模板"（[信号 #72]）——社群在手工求一个"官方在改什么"的订阅通道。mainline-compat 引擎的接口/契约 diff 通知恰好补这个空白。

4. **静默失效是共识痛点**：skills 迁移静默失效（[Issue #67]）、TUI 不显示 skills 生效情况（[Issue #69]）、skill 缓存与模型列表长期不一致（[Issue #208]）、Web 端 skill 永远无法使用（[Issue #62]）——"装了没反应"是最高频抱怨形态，说明**可观测的兼容性检查本身**就是产品价值：在插件安装/升级时自动 diff 主接口并报告失效点，比事后翻轨迹高效得多。

## 5. 结论：插件开发者应该从群里获得什么（可执行建议清单）

1. **窗口期内提交接口/协议类 issue**：趁"内测 issue 可纳入版本"（[信号 #0]），把插件格式标准（#171 生态入口、ContentBlock 语义对齐 MCP #47、hooks 挂载点 #189）作为正式提案提交到 `dsh2026/issues`，并附复现/设计文档。
2. **以 Cordis 插件为底座开发，避免 fork 魔改**：个人 repo 会被官方快照反复覆盖（纪事 07-31~08-03 四连推），本地魔改必漂移；正确姿势是写成插件 + 提交 PR（[信号 #88]）。
3. **订阅官方版本变化并建立兼容基线**：从 snapshot-20260803T142347Z 起官方附 Changelog（[信号 #35]），插件作者应把每个快照的 Changelog 与自身依赖（`@cordisjs/plugin-loader` 等 rc 包，[信号 #111]）做 diff 登记。
4. **交付 skill 时自带验证与可见性**：针对"装没装上不知道"（#68/#69）与"静默失效"（#67/#62）的现状，插件应附带 `dsh skills` 自检说明、明确目录（`.dsh/skills`/`.agents/skills`），并在 README 声明不支持 `.claude/skills`。
5. **锁定构建环境**：pnpm 锁版本（对 11.x，[信号 #108]）、node 走 nvm 24（[信号 #80]）、Windows 按 WSL2 SOP 走（[信号 #79]），插件工程自身同样适用，避免把构建问题混入功能 bug。
6. **群内先确认、后 PR**：官方明示存在"已在做的快要合并的 PR"（[信号 #88]），动手前在群内或 issue 下打招呼（[信号 #83]），避免重复劳动；issue 仓库权限与源码权限分离（[信号 #33]），没权限先在群里反馈（[信号 #102]）。
7. **把兼容性监控当产品做**：群聊反复出现的版本漂移、补丁失效、静默失效、接口变化不可见（见第 3 节），正是 mainline-compat 引擎的落点——对插件开发者而言，维护一个"官方每快照的接口/依赖 diff + 失效告警"通道，就是当前社群最缺的公共设施。
8. **押注两个高价值方向**：多模型集成（subagent 指定模型 [信号 #95]、skill 补多模态 [信号 #1]、外部 harness 联动 [信号 #96]）与自我进化（agent 自装插件 [信号 #100]、dsh-self-iteration [Issue #163]）——前者需求已被反复提出，后者官方尚未落地，均有插件先行的空间。
