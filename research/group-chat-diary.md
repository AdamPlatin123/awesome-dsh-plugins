# group-chat-diary 调研摘要

## 一句话定位
DSH（DeepSeek Harness）内测期间「【官方】DSH内测群」微信群的每日归档仓库：把本机微信数据库里的群聊精选、成员画像、事件纪事与 GitHub Issue 汇总，烘成一个**单文件、自包含、绿色终端风**的交互式 HTML，仅供授权内部成员本地打开查看。

## 技术栈与依赖（语言、框架、关键依赖）
- **形态**：零依赖单文件 HTML（273 KB），样式 / 交互脚本 / 当日快照数据全部内嵌；浏览器双击即用，不依赖同目录任何 JSON/JS。
- **前端实现**：原生 HTML + 内联 CSS + 原生 JS（无框架、无构建）。设计语言为 CRT 终端绿黑风（`#33ff66` / `#030703`、扫描线、闪烁、HYPERSPACE WARP 开场）。
- **数据采集链路（外部、不在本仓库）**：本机微信 4.x 数据库 → `wechat-cli 0.2.4`（`https://github.com/huohuoer/wechat-cli`）导出 `raw-messages.local.json` → 确定性脚本（`deterministic-evidence-backed-v4`，明确标注**未用 LLM 推断身份 / 未用 LLM 给信号打分**）→ 烘进 HTML 的 `globalThis.__DSH_SNAPSHOT__`。
- **Issue 数据源**：GitHub Issues API（仓库 `dsh2026/issues`，详见下文风险点）。
- **无 package.json / 无构建配置 / 无 CI**：纯产物仓库。

## 文件结构概览
```
group-chat-diary/
├── README.md                          2.0 KB  说明用途、命名、隐私边界、更新方式
└── DSH内测群每日档案-0804.html        273 KB  当日归档（含内嵌快照 JSON）
```
（顶层仅 2 个文件；depth=1 clone 仅见 1 个 commit，无其他历史文件。仓库描述「72KB」与实际 273 KB 不一致，可能描述滞后。）

HTML 内部结构（5 个 panel，由 nav tabs 切换）：
- `01 // CHRONICLE` 事件纪事 — 完成态原话 + 事件词候选事件
- `02 // SIGNALS` 信号收录 — 精选发言，带分类筛选
- `03 // PERSONA` 成员星卡 — SSR/SR/R/N 抽卡式成员卡（可翻面）
- `04 // ISSUES` Issue 汇总 — 内测 Issue 分组聚合
- `05 // STAR DATA` 星域数据 — 24h 活跃柱状图 + 群聊/Issue 词云

## 核心功能与实现要点
1. **内嵌快照、离线自洽**：`<script>globalThis.__DSH_SNAPSHOT__=...</script>`（`DSH内测群每日档案-0804.html:266`）一次写入群聊 + Issue 全量数据；`EMBEDDED_SNAPSHOT` 优先于 `fetch(DATA_URLS)`，所以 GitHub 预览页不跑脚本也能"原汁原味"打开。`fetchJson`（`:284-294`）同时保留对外部 `group-data.json` / `issues.json` 的回退路径。
2. **五面板交互**（`initTabs` `:310`、`renderCards` `:409`、`renderSignals` `:359`、`renderChronicle` `:340`、`renderIssues` `:502`、`renderData` `:575`）：纯客户端渲染，按信号分类 / Issue 重要性 / 星卡稀有度动态筛选、排序、搜索，无后端。
3. **群聊信号筛选**（snapshot `quality` 字段）：从 6104 条源消息排除 312 条系统通知 + 27 条系统文本，得 5765 条有效发言；从 177 候选信号按"信号阈值 7 / 每人 ≤12 条 / 每类 ≤36 条"筛出 120 条精选信号，分 5 类（协作流程 36 / 需求建议 36 / 问题反馈 31 / 实测发现 14 / 使用方案 3）。
4. **成员画像星卡**（109 张）：每张含昵称、消息数、入选信号数、LLM-未参与推断的角色（如「Issue 协作 · 协作推动者」）、特质标签、代表性发言。前三名按消息量：成员甲 899 / 成员乙 673 / 成员丙 590（昵称已脱敏）；维护者本人（昵称已脱敏）196 条（`self:true`）。
5. **事件纪事候选**（4 条，全部 `confidence:"candidate"`）：
   - 7/31 21:25 群内发布账号（昵称已脱敏）：本群成员获 DSH 内测代码仓库访问权限；
   - 8/01 21:13 群内发布账号：推送 `snapshot-20260801T124809Z-4384d33896`（无功能清单）；
   - 8/03 00:24 群内发布账号：推送 `snapshot-20260802T160331Z-2ad87c3d0b`（无功能清单）；
   - 8/03 22:43 群内发布账号：推送 `snapshot-20260803T142347Z-25b2ad4f67`，**附完整功能清单**（见下）。
6. **Issue 聚合**：217 条 issue（209 open）/ 16 个分组（bug修复 5 组、功能建议 10 组、无效记录 1 组）；按 `score` 排序，Top 3 分组为「卡死、中断与重试」「权限与隔离环境」「数据安全与会话恢复」。每条 issue 链接到 `https://github.com/dsh2026/issues/issues/<n>`。
7. **隐私自洽**：README 明确「页面只保留聚合统计、精选信号、成员画像和事件候选，**不包含完整聊天记录、微信数据库或解密密钥**」；身份规则——左侧气泡为他人、右侧绿色气泡为维护者本人（昵称已脱敏）。

## 与 DeepSeek Harness 主仓库的集成点
**归档/旁观层，与 DSH 主仓库无代码级 seam**：
- 不发布插件、不发 CLI、不暴露协议；产物仅一份 HTML。
- 集成是**语义级**的：(a) Issue URL 指向 `dsh2026/issues`（DSH 内测 Issue 跟踪仓库）；(b) 纪事里的 snapshot tag（`snapshot-2026080*`）就是 DSH 主仓库内测版本的 git tag。
- **没有自动上传链路**：README 明确「每日 HTML 尚未自动上传到本仓库。只有经过明确确认的文件才会提交到这里」；维护者（昵称已脱敏）每天 05:00 本机生成，但提交靠人工。

## 亮点与风险
**亮点**
1. **零运行时依赖、纯静态、可永久归档**：单文件 HTML 适合作为长期证据物，几年后打开仍可用，无供应链腐烂风险。
2. **证据可追溯性做得严肃**：每条 chronicle 带 `message_id` 和 `source_ref: sha256:...` 指纹；`quality` 字段公开采集方法学（阈值、各类上限、拒绝计数、`chronicles_are_candidates:true`），明确「不用 LLM 给身份/信号打分」，规避了 LLM 编造风险。
3. **隐私分级清晰**：原始记录留在本机，公开层只发布聚合 + 精选；README 反复强调不可转发、不可开 GitHub Pages。
4. **设计有信息密度**：5 面板覆盖「事件 / 信号 / 人物 / Issue / 数据」五个维度，星卡抽卡化降低阅读疲劳。

**风险**
1. **PII 与隐私泄露面大**（`DSH内测群每日档案-0804.html:266` 整个内嵌 JSON）：109 名成员的真实微信昵称、角色定性、代表性发言原文（部分含主观评判，如涉及成员间截图/泄密争议的发言，昵称已脱敏）全部进入仓库；private 仓库无法阻止已授权者下载外传——README 自己也承认这一点。
2. **README 与实际数据指向不同的 Issue 仓库**：README 写 `dsh-external/issues`，但 snapshot 内 `issues.source.repository = "dsh2026/issues"`，issue URL 也是 `github.com/dsh2026/issues/issues/<n>`（`snapshot.json` → `issues.source`）。文档与数据不一致，后续读者可能找错仓库。
3. **纪事只是候选**：4 条 chronicle 全部 `confidence:"candidate"`，标题如「内测版本更新」是模板化生成，前两条甚至没有功能清单；据此精确还原 DSH 功能演进**只能依赖 8/03 22:43 这一条**，更早版本（4384d33896、2ad87c3d0b）的变更内容不可恢复。
4. **更新机制是手动的**：README 称每日 05:00 本机生成 + 人工确认提交；当前仓库只有 1 个 commit（`b3f6369` 2026-08-05「docs: move daily refresh to 05:00」），未见到自动同步证据，存在断更风险。
5. **身份规则不对称**：`identity_rules.right` 与 `self:true` 都指向维护者本人昵称（已脱敏），但 commit author 是另一个真实姓名（已脱敏），两者关系不透明，外部读者难以判断谁是维护者。

## 备注
- **时间跨度（关键）**：当日归档实际覆盖 `2026-07-31T17:51:13+08:00` → `2026-08-04T16:25:17+08:00`，共 **约 4 天（3 天 22 小时 34 分）**——并非文件名暗示的"8/04 当天"，而是**从 DSH 内测群成立那一刻起截至 8/04 下午**的累积快照；生成于 `2026-08-04T16:34:44+08:00`（`generatedAt`）/ `2026-08-04T08:25:32Z`（issues.updated_at）。
- **能否提取 DSH 功能演进信息**：**部分可以**。3 条 `snapshot-*` tag 形成清晰版本轴（8/01 → 8/02 → 8/03），且 8/03 22:43 的 `snapshot-20260803T142347Z-25b2ad4f67` 附带可见变更清单：
  - 新增：对话直接展示远程 Markdown 图片（本地文件 / 非安全协议仍不加载）；
  - TUI 新增 `/details` 命令与可视化选择器（控制工具卡片 / 推理内容显示方式）；
  - 修复：非 localhost 访问无法完成欢迎引导（敏感接口远程访问仍禁止）；
  - 失败 Bash 命令可展开查看原始参数与完整错误；
  - 优化：工作区路径选择器目录面板支持前进 / 后退。
  但前两个 snapshot 无功能清单，**早期版本演进需结合 `dsh2026/issues` 仓库 + 主仓库 git log 才能完整还原**——这正好印证「旧 session 用群聊讨论对齐代码库」的用途：群聊纪事是事实时间轴，issue 是细节源头。
- **活跃时段**（每小时消息量）：峰值 15-16 点（505）、20-22 点（380/481/470）；凌晨 4-7 点几乎为零（3/0/2/75）——符合"内测群白天 + 晚上活跃、凌晨静默"的作息。
- **群聊 vs Issue 主题对比**：群聊高频词（Issue 177 / 模型 155 / 插件 131 / 会话 124 / Agent 100 / Web UI 74 / 安装 50 / Windows 49）与 Issue 分组（卡死中断重试 22 / 权限隔离 17 / 文件预览 16 / 数据安全恢复 10）相互印证：群聊偏"功能讨论 + 协作推动"，Issue 偏"具体 bug + 体验诉求"。
- **数据完整度建议**：若要做"超级调研报告"，建议把本仓库当作 **DSH 内测**时间轴与人脉图**的索引层**，真正的代码 / Issue 细节去 `dsh2026/issues` 与主仓库查；本仓库的增量价值是**成员画像 + 群聊原话精选**，这在 issue 仓库拿不到。
